# Devlog 3: the spike grows four tests, and the open questions get answered (2026-10-23)

**One thing before the results.** Every decision in this entry was made by the
AI assistant, under an explicit delegation from the founder to decide the
remaining Phase 0 questions and finish the work. The reasoning is written down in
`docs/adr/2026-10-23_Phase0-Founder-Decisions_v1.md`, including the fact that no
founder line-by-line review has happened yet. If you read a choice below and
think "that is the founder's call", it probably is, and it is open to reversal.
What the assistant did not do is pick a reading that makes a kill criterion
easier to pass; in every case where two readings existed, the stricter one was
chosen.

## The spike now has 16 scenarios, and they all pass

Four scenarios were added to close the gaps that the 2026-10-18 entry listed as
open. On the same stock Fedora 45 Beta VM (kernel 7.2.0-61, aarch64, SELinux
enforcing), **16 of 16 pass in three consecutive runs**, and each run's log is
committed under `docs/spike-results/`.

- **Can a session leave itself?** No. An unprivileged in-session process that
  writes its own pid into another cgroup's `cgroup.procs` gets `EACCES`, both for
  a sibling scope and for the cgroupfs root, and gets `EACCES` when it tries to
  create a sub-cgroup under its own scope. It still raises its label afterwards,
  so the refusal is not the process having quietly escaped. The honest asymmetry:
  root *can* write that file. The guarantee comes from the session having no
  privilege, not from the kernel being able to say no to root.
- **Does a label go away when the reason for it goes away?** Partially, and that
  is the interesting result. Raising a file's attribute from private to secret is
  honoured on the next open. Adding a directory rule is honoured, and removing it
  un-labels the next open exactly. **Removing the attribute is not honoured: the
  label stays raised.** That is the inode cache behaving exactly as designed - it
  is a floor, it can only add certainty, never remove it - and declassification
  removes.
- **The 10,000-iteration race, in both readings the design document asks for.**
  The opener samples its own label right after `open()` returns, and a separate
  process outside the session samples it after receiving a byte from the opener.
  10,000 iterations each, **zero misses**, three runs. The first attempt at this
  test reported 4,621 observer misses and that was my harness, not the kernel: a
  one-way notify byte over a buffered socket lets the writer clear the slot again
  before the observer has read it. Adding an acknowledgement roundtrip fixed the
  measurement; the kernel behaviour was never in doubt, but I nearly recorded a
  kernel failure that was a bug in my own test.
- **Latency, so the next decision is not a guess.** 20,000 measured
  `open()`+`close()` iterations per case. An open outside any session costs 835
  ns at p50; inside a session on an unlabelled file 1,211 ns; on an
  xattr-labelled file also 1,211 ns; with a matching directory rule 1,252 ns; on
  the path where the label is actually raised, 1,711 ns. The labeller adds about
  376 ns at p50 to a session's opens. These are numbers with a loaded probe in
  one Go process, so they bracket `open(2)` and nothing else, but they are enough
  to decide what they were measured for.

## The cache question, answered by taking the cache out

The design allowed two lookup methods: read the file's attribute on every open,
or keep an inode-keyed cache. The measured overhead of the read path is small and
the measured correctness cost of the cache is not, so **the production labeller
keeps no inode cache.** To check that this was a decision and not a preference,
the loader got a switch (`TM_DISABLE_INODE_CACHE=1`) that compiles every cache
read and write out, and the whole 16-scenario suite - overlay case included -
passes 16 of 16 that way. The attribute-removal case then reads "unlabelled"
exactly as it should.

A side effect: the kernel-floor argument that rested on the cache's one kfunc
(`bpf_real_data_inode`, new in Linux 7.2) evaporates. The floor stays at 7.2
anyway, but now for an honest reason: nothing has been tested on 7.1, and this
project says nothing it has not measured.

## The licence contradiction, fixed and re-tested

The BPF object declared `GPL` to the kernel while its file header said
Apache-2.0. The kernel only lets GPL-compatible objects call the LSM kfuncs, so
the two could not both be true, and a project that sells signed metadata cannot
ship metadata that contradicts itself. The sources are now
`GPL-2.0-only OR BSD-2-Clause` with the conventional `Dual BSD/GPL` tag, the
exception is recorded in `NOTICE`, and the object was rebuilt and re-run to prove
the kfuncs are still accepted: 16 of 16.

## The remaining aliasing decision

A hard link or a move out of a protected folder gives the file a path that no
rule matches. The two options were to bind the label to the file's content (stamp
an attribute so the label follows the inode) or to keep labels tied to the
location and refuse the operations that would break the promise. **Location, with
refusal:** from Phase 1 the labeller denies an in-session link or rename whose
destination is not under the same rule as its source. Stamping attributes from
kernel hooks would give the labeller write authority the threat model does not
grant it, and it would keep a private label on a file someone deliberately
published. What this spike cannot show is the enforcement itself, because the
probe only observes, never denies - so that is Phase 1 work with a real risk
attached, written into the ADR rather than smoothed over.

## Other decisions taken

- Interview coding rules: frozen 2026-10-23 with every default kept, because each
  default is the stricter reading. The SHA-256 of the frozen rules, guide and
  screener is in devlog 1. The freeze is four days late against the checklist and
  is logged as a deviation.
- Budget: the two Phase 0 records that no gate criterion reads - shared-folder
  behaviour on virtiofs/9p and Lima cloud-init provisioning on a bootc image -
  move to Phase 1. That makes Phase 0 31.75 hours against a 30-hour plan. macOS
  users with data in shared folders stay outside every claim until that
  measurement exists.
- Kill criteria: the concept document's full wording governs both criteria,
  because that is what the public reads, and a triggered criterion cannot be
  overridden.
- Security scanners: gosec, govulncheck and CodeQL arrive in Phase 1 week 4,
  when there is root-running product code for them to look at. Phase 0 has gofmt,
  `go vet` and shellcheck, and a spike loader.
- The repository now exists, as `github.com/BitecodesHub/tidemark`, **private for
  the moment**. It was created so the x86_64 CI spike and the signed-image
  pipeline could actually run; making it public stays a launch decision. The Go
  module path stopped being a placeholder at the same time.

# Devlog 4: the second architecture, and a pipeline that stops short of publishing (2026-10-23)

Same standing disclosure as devlog 3: the founder delegated the open Phase 0
decisions to the AI assistant ("you decide everything and stop when done"), the
reasoning is in `docs/adr/2026-10-23_Phase0-Founder-Decisions_v1.md`, and no
founder line-by-line review has happened yet. Where two readings of a checklist
item existed, the stricter one was used, which is why several boxes below stay
open on purpose.

## Criterion 1 now has two architectures

The x86_64 half ran. **16 of 16 scenarios, four consecutive green CI runs** under
QEMU/KVM on a GitHub-hosted runner, in a stock Fedora 45 Beta cloud guest (kernel
`7.2.0-61.fc45.x86_64`, SELinux enforcing, Landlock ABI 10, BTF present, lockdown
`[none]`). One run was a push, three were manual repeats to prove it wasn't a
fluke; the transcripts are committed as
`docs/spike-results/2026-10-23_Spike-Run-x86_64-ci_v{1,2,3,4}.log`, and after
substituting pids, temp paths and every numeric timing field, the four are
line-identical.

The part worth reading is not the pass count, it's the agreement. On both
architectures: the 10,000-iteration raise-before-`open()`-returns race with zero
misses in both the opener and a separate observer; overlayfs raising with
`cause=open|xattr|backing`, which is the signature of the backing-file open; a
descriptor passed with SCM_RIGHTS raising `open|receive`, and an unprivileged
receiver failing closed to `TM_LABEL_UNKNOWN` with `receive|error|eacces`;
`EACCES` for both cgroup move-out attempts with root still able to do it;
`PROT_WRITE` on the label word refused, and a writable `BPF_F_RDONLY` mapping
refused; and the two known holes reproducing identically - a mount-namespace alias
and a hard link out of a ruled root both read `label=0x0`, and removing an
attribute leaves a cached label raised (`open|cache`). A kernel behaviour that
only fails on one architecture would have been a much more expensive bug to find.

Latency does *not* agree, and the difference is instrumentation, not kernel:
the labeller's p50 delta over the outside-session baseline is about **+0.38 µs**
in the Lima VM and about **+1.56 µs** in CI. The CI guest is given 4 vCPU on a
runner whose KVM documentation recommends 2, so every timer in that guest is
competing. Both numbers are floors measured around `open(2)` inside one process
with the probe loaded; neither is a product number, and Phase 0 sets no target.

## The first x86_64 run failed because of a tty

Worth keeping, because it is the kind of failure a gate must not be able to
produce. The spike ran inside a cloud-init `runcmd` whose output went to
`/dev/ttyS0`, and the workflow grepped a result marker from that serial log. The
runner exited `qemu exit code: 0` with no marker and no explanation. Midway
through the dnf transaction, `serial-getty@ttyS0` restarted; a getty restart
calls `vhangup()`, which replaces the file operations of every *already open*
descriptor on that tty, so the provisioning shell's stdout was now pointing at a
hung-up tty and every subsequent write returned `-EIO`. The run had almost
certainly passed; the gate simply could not read its own result.

The job now drives the guest over SSH through QEMU user-mode networking with an
ed25519 key generated for that run and thrown away after, keeps the serial log as
boot and oops evidence only, and ships the source as an ISO built from
`git archive HEAD spike` rather than the working directory - because the local
tree carries aarch64 `.o` files newer than every source file, and a guest could
have "passed" while reusing a binary built for the wrong architecture. The x86_64
objects are compiled from `-target bpf -mcpu=v3 -D__TARGET_ARCH_x86` against a
regenerated `vmlinux.h`, and the environment capture says so.

## The base images we pinned had been deleted

Both digests pinned on 16 October stopped resolving: quay.io garbage-collects the
manifests of daily-rebuilt tags once they age out, and `fedora-bootc` is rebuilt
daily. That is not a hypothetical risk in the threat model, it is the model's
premise - "this commit built this image" is only a claim if the digest still
resolves. Re-pinned by hand to `:45@sha256:4c714111…` (45.20261023.0, kernel
`7.2.11-300.fc45`) and `:44@sha256:03808453…` (44.20261023.0), each verified
against the registry with its child arch digests and the kernel read back out of
the image config. A composite action now checks reachability before every build
and fails naming the current digest. It never rewrites a pin: an automatic
refresh would let an image labelled with one digest carry another compose's
content, which is the failure mode the pin exists to prevent (PD-14).

## The image pipeline is green, and deliberately stops one step short

Both variants build in about 6 minutes, each producing a syft SPDX SBOM and a
report-only trivy scan from the OCI archive with no network and no credentials;
the qcow2 built by bootc-image-builder boots twice under QEMU/KVM with no network
and passes the in-image self-test both times, at 10.4 s and 9.1 s of guest uptime,
on `7.2.11-300.fc45.x86_64` with `selinux=enforcing`, `landlock_abi=10` and the
two kfuncs the labeller needs reported as `ok`.

The publish job was about to run. Its condition was "image inputs changed, push to
main", and on the run above it became reachable the moment the Fedora 45 boot test
turned green. Publishing pushes to GHCR and signs keyless with cosign, and keyless
signing writes a **public, permanent entry to the Sigstore transparency log** -
which is the point of it - naming this repository and its digests. That log is
mirrored and searchable and cannot be retracted; a private, unlaunched repository
getting a permanent public record of its build artifacts is exactly the kind of
irreversible side effect that should not happen by default. I cancelled the run
with the publish job still queued (the builds and the boot-test evidence were
already captured), and publication is now opt-in behind a repository variable,
with a job that writes into every image run why it did or did not publish
(PD-17). Consequence stated plainly: **AC6 is not met.** A signed image is one
`gh variable set PUBLISH_IMAGES --body push` away, and flipping it is the
founder's call, best made together with making the repository public.

## Repository hygiene, item by item

DCO sign-off is now enforced by a workflow that checks the `Signed-off-by` trailer
on every commit under review and warns when the trailer isn't the author (PD-11
chose DCO over a CLA). It does not fail on the very first commit of this
repository, which carries no trailer - rewriting published history to make a
checker green is a worse trade than one recorded exception.

Branch protection is **off**, decided rather than forgotten (PD-18): a solo
repository that commits evidence transcripts and doc fixes to `main` in the same
hour a CI run finishes does not benefit from a required-check rule whose only
reviewer is the same person, and it is a one-minute change to add when a
collaborator appears. Secret scanning and push protection are simply not
available to a private repository on this plan - both API endpoints answer 404 -
so there was nothing to enable; dependency alerts and the dependency graph *are*
on. The OpenSSF Scorecard workflow stays non-gating for the same credential reason
recorded in PD-15.

One honest correction came out of writing that paragraph. E4 asks for gofmt and
staticcheck, and both checklists and decision records described them as already
running in CI. They were not: `lint.yml` had actionlint, shellcheck, a
policy-schema check and a link check, and the only Go check anywhere was `go vet`
as the last line of `make build` inside the spike guest. So `lint.yml` gained a
`go-quality` job - Go 1.27.3 pinned by SHA-256, deliberately the same toolchain
the guest builds with so a formatting or vet difference between the two
environments cannot appear, plus staticcheck v0.8.2 - and E4/T5 now say what its
first run showed instead of asserting a check that did not exist. That is the kind
of claim this project is supposed to be careful about, and the mistake was mine,
made while writing about CI at speed.

## What is still not done, plainly

- **Interviews: zero of eight.** Kill criterion 2 has no evidence at all, and none
  of today's work makes up for it. This is the thing most likely to fail the gate.
- **The gate record itself** (I1) and devlog 3's promised 8 November entry. The
  section 6 table is now evidence-filled for both architectures so the decision
  can actually be made; making it is founder work.
- **Fedora 45 GA.** Both spike architectures pinned the Beta kernel `7.2.0-61` on
  purpose. The boot test runs a `7.2.11` image, which is closer to GA, but the
  16-scenario suite has not been run on a GA kernel on either architecture.
- **The probe inside the booted image.** The boot test boots the image and runs
  its self-test; it does not load `label_probe.bpf.o` inside it, because the Phase
  0 image ships no enforcement. That is D2, deferred by PD-6 - so E3 and T2 stay
  open with that reason attached.
- **`TM_DISABLE_INODE_CACHE=1` has only ever run on aarch64.** The no-cache design
  (PD-1) is therefore measured on one architecture; the x86_64 runs used the cache
  as an instrument.
- **Publication**, as above: one command, deliberately unrun.
- Founder review of every AI-drafted document, including this one, and promotion
  of the labeller ADR from Proposed.
